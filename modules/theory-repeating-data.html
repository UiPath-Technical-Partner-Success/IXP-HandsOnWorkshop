Theory · Repeating data

📅 Day 1📖 TheoryThen: Lab 2

🔁 Repeating data

⏱ Day 1 · 1:20–1:55 · Theory + Lab 2

Takeaway: when the same information appears several times – accounts, line items, parties – model it as one field group. The model returns one row (one extraction) per occurrence, whether there are 2 or 20.

One field group, one row per occurrence

What it isA field group is a table: its fields are columns and each occurrence the model finds in the document is a row, called an extraction. The Account group with Account Number, Currency and balances returns 4 rows for a 4-account statement.
What it doesIt replaces numbered fields (Account 1 Balance, Account 2 Balance…) with one definition that works for any count. A key field (such as the account number) in the group keeps occurrences apart and makes each row traceable.
When to useAny value set that repeats: accounts per currency, invoice lines, policy holders, transactions. When not: values that appear once per document (bank name, statement date) belong in a separate header group, so they are not repeated on every row.
How to use
  1. Create one group (for example Account) with the per-occurrence fields.
  2. Group instruction: "One occurrence per bank account listed. Each account has its own section… Extract every account, in the order they appear."
  3. Say which part of the document to use if the same data also appears in a summary table.
  4. Use Monetary Quantity for amounts so the currency travels with the value.
Common mistakes
  • Numbered fields: they break as soon as the count changes and leave empty slots on shorter documents.
  • The same account picked up twice, from a summary table and from its detail section. Fix it in the group instruction.
  • No unique key field: two accounts with the same currency become hard to tell apart.
  • Exceeding 32 fields in one group: split the entity, or use a child group.

Parent and child field groups (nested repeating data)

What it isA child group sits under a parent group, written Parent > Child, for example Account > Transactions or the docs' Invoice > Line Items.
What it doesThe parent acts as a gate: if no parent is predicted, the child returns nothing. The parent's instructions do not influence the child, so the child needs its own instruction.
When to useA repeating structure inside another one: transactions per account, line items per invoice, assets per portfolio. When not: do not nest unrelated data under one parent (address and holdings under "Account Owner") – the hierarchy should mirror the document.
How to use
  1. Manage Taxonomy → on the parent group select Add → New field group.
  2. Write a child instruction that stands on its own (what a row is, where the table is).
  3. Include the parent's key field if you need to join rows later.
Common mistakes
  • Relying on the parent instruction to explain the child table.
  • A parent group that is rarely found, which silently hides all child rows.
  • Unrelated child groups under one parent, which confuses the model.

Reviewing repeating data

What it isAt design time: the table view on the Validate predictions page. At runtime: Validation Station, where IXP Unstructured and complex documents results are always validated as tables.
What it doesShows each occurrence as a row so a reviewer can compare row by row with the document, add a missing row, and confirm correct rows. Field filters in Validation Station help reviewers focus on what is left to check.
When to useEvery time a group can repeat. When not: do not bulk-confirm a whole group unless every row is correct.
How to use
  1. Validate predictions → select the table icon.
  2. Check row count against the document first, then values.
  3. Confirm correct rows; correct or add the rest; submit the document.
Common mistakes
  • Confirming a whole group when only some rows are right: the wrong rows become "correct".
  • Checking values but not the row count: a missing account is a missed prediction too.
💬 "The same information appears several times (4 bank accounts, one per currency). How do we extract it?"

Create one field group, for example Account, with the fields one account has: account number, currency, opening and closing balance. The model returns one row per account it finds, so the same design works for 2, 4 or 10 accounts. Add a group instruction that says what one account is and which section to read, and keep the account number as a key. If each account also has transactions, add a child group Account > Transactions with its own instruction. Review the result in table view, row by row.

💡 Key takeaways
  • Repeating information = one field group, one row per occurrence.
  • Use a unique key field and say which part of the document to read.
  • Child groups need their own instruction and only appear when the parent is found.
  • Review repeating data in table view, row by row.
