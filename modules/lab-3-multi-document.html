Lab 3 · Multi-document files

⏱ ~30 min🔨 Hands-onSession 1
📖 Read first: Session 1 theory – Multi-document files (packets) explains what a packet is, why IXP (Intelligent Xtraction and Processing) extraction doesn't split a packet, and when to classify and split first instead of sending the whole packet to one project.
What you are doing and why

Customers rarely send one clean document per file. A loan or onboarding request often arrives as one PDF with an invoice, a bank statement and a payslip stuck together. In this lab you process such a file in two ways and measure which one works better.

At the end you will have: one IXP project that reads the whole packet (approach B), separate per-type extractions from a split packet (approach A), and a filled-in comparison table you can turn into a decision rule.

In a real project this is the first design decision for any document intake that receives mixed files: do we put a classification and splitting step in front of extraction, or not? Getting it wrong costs either accuracy (values mixed between documents) or complexity you did not need.

Terms used in this lab

Already explained earlier, so not repeated here: IXP and DU (Document Understanding) in Session 1 – Foundations; field group and field group instructions in Session 1 – Glossary; packets, classification, splitting and page ranges in Multi-document files. New in this lab:

Mix-up
A value taken from the wrong document, for example an account number from the payslip landing in the Bank Account group.
Consumption
IXP and DU processing consume units from your organization's UiPath license. IXP extraction is metered per page; the licensing FAQ has the details for your plan.

🎯 Objective

Process one PDF that has several document types in it (invoice + bank statement + payslip). Compare two approaches and decide when you really need to split first.

Approach A – Classify + split, then IXP per type Approach B – One IXP project on the whole packet
How A DU classifier finds the document type and page range of each document, then each part goes to the IXP project for its type One project with a field group per document type (Invoice, Bank Account, Payslip)
Strength Clean separation, one model per type, easy to reuse Fewer moving parts, one call
Risk More steps and calls, splitting errors carry over (including over-splitting: one multi-page document cut into separate parts) Large taxonomy, fields can get mixed between types, harder to maintain
Four facts to know before you start
  • IXP extraction doesn't split or classify. The Unstructured and complex documents capability returns your fields. It doesn't tell you where one document ends and the next begins, and the Advanced strategy's multiple passes don't change that. In approach A, the splitting must come from a DU classifier.
  • IXP can read stacks without splitting. The docs list extracting data from several document types combined in one file, without splitting them first, as a use case for this capability. That is approach B.
  • Page limit depends on the extraction model. Per the IXP model configuration page, GPT-4o processes up to 50 pages per document and Gemini 2.5 Flash up to 500 pages in a single call; pages beyond the limit are not processed. Check which model your project uses. For packets over the limit, classify and split first.
  • Consumption is per page, not per call. A classifier in front of IXP is metered separately. When every page is extracted, A and B consume about the same; A saves only when it lets you skip pages you do not need (cover pages, blank pages, terms). Check the licensing FAQ for your plan.

📋 Before you begin

✔️ Prerequisites

  • Lab 2 done (the Account group is reused)
  • For approach A: the pre-split PDFs in lab3_split_parts.zip (one PDF per document). The trainer demos the classify-and-split step; in Studio desktop (Windows) projects this is typically the Intelligent Keyword Classifier inside a Classify Document Scope. The IXP project itself cannot split.

📎 Input files

customer_packet_1.pdf, customer_packet_2.pdf, customer_packet_3.pdf (challenge, step 4), lab3_split_parts.zip (approach A)

🔨 Steps

  1. 1
    Open customer_packet_1.pdf and write down the page ranges for each document type.
    Why: this is your ground truth, the correct answer you check both approaches against. Do the same for customer_packet_2.pdf. Tip: each document starts with a title at the top of the page.
    Expected result: Your "ground truth" (packet 1 has 3 pages; packet 2 has 4 pages in a different order, and its statement runs over 2 pages).
  2. 2
    Approach B first. Create project Lab3_Packet_<initials>. Add 3 field groups: Invoice (invoice number, date, supplier, total), Bank Account (one extraction per account, like the Account group in Lab 2), Payslip (employee name, period, net pay). In each group instruction, describe how to recognize that document type.
    Field groups as document types

    A field group bundles fields that belong together. In approach B each group stands for one document type, and its instruction (together with the overall extraction instructions) is what tells the model which pages to read for it. Create the project from the IXP Unstructured and complex documents capability, then in the Build tab select Manage taxonomy to add field groups, fields and instructions.

    A useful group instruction names the visible clues and what to ignore, for example: "Use only the document titled TAX INVOICE. Ignore bank statements and payslips in the same file."

    Expected result: One project, 3 groups.
    📋 Ready-to-use instructions

    Group and field instructions for approach B. For the Bank Account fields, reuse the field instructions from Lab 2. For approach A (step 6), use the same group and field instructions in each per-type project.

    Overall extraction instructions
    Each file is a packet that combines several documents of different types, such as tax invoices, bank statements and payslips, in any order. One document can continue over more than one page. Each field group stands for one document type. Take the values for a group only from the pages of that document type.
    Field group · Invoice
    A tax invoice: a page titled "TAX INVOICE", with the supplier's name and address at the top, an invoice number, invoice and due dates, a "Bill to" block, a table of line items and a "Total due". Use only the pages of this invoice. Bank statements and payslips in the same file are other document types.
    Field · Invoice Number (Exact Text)
    The identifier of the invoice, shown next to "Invoice number" in the invoice header, below the "TAX INVOICE" title. Example: "KOS-2026-01142".
    Field · Invoice Date (Date)
    The date the invoice was issued, shown next to "Invoice date" in the invoice header. This is the issue date, which comes before the due date. Example: "14/09/2026".
    Field · Supplier (Exact Text)
    The company that issued the invoice, printed as the title at the top of the invoice page, above its address and VAT number. The company under "Bill to" is the customer. Example: "Kinneret Office Supplies Ltd.".
    Field · Total (Monetary Quantity)
    The final amount to pay, including VAT, shown next to "Total due" below the line items and the VAT line. Example: "22,484.90 ILS".
    Field group · Bank Account
    A bank statement: pages that start with a bank's name and a statement header (customer, statement period, statement number), followed by one section per account. One occurrence per account section. An account's transaction table can continue onto the next page; that continuation belongs to the same account. Use only the pages of the bank statement.
    Field group · Payslip
    A payslip: a page titled "PAYSLIP", with the employer's name at the top, the employee's name and ID, the pay period and payment date, a table of earnings and deductions, and the net pay. Use only the payslip page.
    Field · Employee Name (Exact Text)
    The person the payslip is for, shown next to "Employee" in the payslip header, below the "PAYSLIP" title. The name at the very top is the employer. Example: "Amir Haddad (fictional)".
    Field · Pay Period (Inferred Text)
    The month the salary is paid for, shown next to "Pay period" in the payslip header. This is the period, not the payment date. Example: "August 2026".
    Field · Net Pay (Monetary Quantity)
    The amount paid to the employee after all deductions, shown next to "Net pay" at the bottom of the payslip, below "Gross pay" and "Total deductions". Example: "18,094.80 ILS".
  3. 3
    Upload both packets and run the extraction.
    What to expect: predictions are generated automatically after upload. If you changed the taxonomy after uploading, open Validate predictions and select Predict extractions to refresh them (Reviewing predictions). Both packets are well within the page limit of either extraction model.
    Expected result: Values for all 3 types in one result.
  4. 4
    Review: are invoice values only coming from the invoice pages? Are there any values from the wrong document?
    Why: in approach B there is no page range per document. The model decides from your instructions which pages belong to which group, so mix-ups only show up when you check. The highlighted references help you find where a value came from, but they can be imperfect, so judge the value itself. On the Validate predictions page, compare each predicted value with the document and your ground truth from step 1. Pay extra attention to packet 2, where the order is different.
    🧩 Challenge: a packet closer to real life

    Packets 1 and 2 are clean: each holds exactly one invoice, one statement and one payslip. Real packets rarely are. Upload customer_packet_3.pdf (5 pages) to the same project, but first write down its ground truth as in step 1: which documents are in it, which pages belong together, and which of your three groups should get values.

    Then review it the same way. Look for values that land in a group although no document of that type is in the file, and for occurrences that don't belong to a real account. Each mix-up you find is a gap in an instruction: fix the group or field instruction, select Predict extractions again and check whether packets 1 and 2 still come out right.

    Expected result: A list of mix-ups (if any), and for packet 3 at least one instruction you changed because of it.
  5. 5
    Evaluate and record the scores, plus how long one extraction took.
    What the scores mean

    Scores compare the model's predictions with values you confirmed (annotations). So first confirm or correct every value on every packet on the Validate predictions page; documents that are not annotated are not counted. The Build tab shows the Project score (the average F1 score across all fields). The Measure tab shows scores per field group and field.

    F1 combines precision (how often a predicted value is correct) and recall (how many of the real values were found). Higher is better. With only a few packets, treat the scores as indicative: the docs recommend at least 10 annotated examples per field. For time, note how long it takes from upload until the predictions appear.

    Sources: Evaluating model performance · Gathering validation statistics

    Expected result: Scores + time per packet.
  6. 6
    Approach A. Watch the trainer's classify-and-split demo, then use the pre-split PDFs in lab3_split_parts.zip: send each part to a project for its own type (reuse your Lab 2 project for the statement).
    How classify-and-split works

    Approach A adds a step that IXP does not have. A DU classifier reads the packet and returns a list with one entry per document: its type and its page range (for example Payslip p1, Bank statement p2–3, Invoice p4). Your automation then sends each range to the IXP project for that type. In a Studio desktop (Windows) project this is typically a Classify Document Scope with the Intelligent Keyword Classifier, which is documented as able to split packages into document types. In this workshop the trainer demos that step and you start from the split files, so your lab time goes into extraction and the comparison.

    • Check the split before extraction. Compare the returned page ranges with your ground truth from step 1. A wrong boundary sends the wrong pages to the wrong project.
    • Watch for over-splitting. The statement in packet 2 runs over 2 pages. If the classifier cuts it into two 1-page parts, each half is extracted without the other.
    • You need one project per type. Reuse Lab 2 for the statement. For the invoice and payslip, create two small projects with just that one field group (same fields as step 2), or use the trainer's projects.
    • The split files. The zip holds one PDF per document, named by packet, type and page range (for example packet2_bank_statement_p2-3.pdf): the same list a classifier returns. Upload each file to the matching project.

    Sources: Document classification overview · Intelligent Keyword Classifier

    Expected result: 3 separate extractions.

❓ Checkpoint questions
  1. Your customer's packets always contain the same 2 document types in the same order. Which approach do you choose?
    Show answer
    Approach B, one project with one field group per type. With few, fixed types no split is needed, and you keep one project and one call. Write group instructions that name each type's visible clues, and check for mix-ups between groups.
  2. Packets contain any of 15 document types in any order. Which approach do you choose?
    Show answer
    Approach A, classify and split first, then one project per type. Fifteen groups in one project make a large taxonomy where values mix between types, and every new type means changing that one project. Splitting also lets you skip pages you don't need.
  3. If you ran approach A, what happens to extraction when the splitter puts a page in the wrong document?
    Show answer
    The wrong pages go to the wrong project. Values go missing from one document and can turn up in another, and extraction can't repair a split error. Check the returned page ranges, or validate the classification, before you extract.
  4. In the challenge packet, what should the Payslip group return, and why is that hard for approach B?
    Show answer
    Nothing: packet 3 has no payslip. A salary credit on a bank statement is not a payslip, but it carries a salary amount and an employer name, so a weak group instruction fills the group anyway. In approach B the model must decide from your instructions alone that a type is missing. In approach A the classifier simply returns no payslip range, and the payslip project is never called.
⚠️ Common mistakes
  • Splitting by default. If the packet is predictable and small, one project with good group instructions can be simpler.
  • Not splitting when you should. Many types, a variable order, or very long packets usually need classification first.
  • Expecting IXP to split the packet. IXP is extraction only. Document boundaries come from a DU classifier or from your group instructions.
  • Group instructions that don't say how to recognize the document, so fields get pulled from the wrong pages.
  • Not checking the split. Over-splitting (one multi-page document cut into parts) or a wrong boundary silently feeds the wrong pages to extraction. Validate splitting separately from extraction.
  • Sending packets over the page limit. The limit depends on the extraction model (50 pages for GPT-4o, up to 500 for Gemini 2.5 Flash). Pages beyond it are not processed.
  • Not measuring time, number of calls and pages processed. Cost and speed are part of the decision, not just accuracy.
🚀 Stretch goals
  • Add a 4th document type to approach B and see how scores change for the existing groups.
    Show how

    The packets contain only 3 types, so use the 4th type as a negative test: add a group for a type that is not in the files. Field group Purchase Order:

    A purchase order: a page titled "PURCHASE ORDER", issued by the buyer, with a PO number, an order date, the supplier and the ordered items. Use only the pages of a purchase order.

    PO Number (Exact Text)

    The identifier of the purchase order, shown next to "PO number" or "Order number" in the purchase order header, below the "PURCHASE ORDER" title. Example: "PO-2026-0815".

    Order Date (Date)

    The date the purchase order was issued, shown next to "Order date" in the purchase order header. Example: "10/09/2026".

    Expected result: no values for Purchase Order. Any value that appears was taken from another document, most likely the invoice, which is a mix-up. Then compare the scores of the 3 existing groups with your earlier run: a bigger taxonomy should not make them worse.

    Optional: upload one anonymized document of a real 4th type from your own projects and repeat.

  • Write a short "decision rule" for your team: "We split first when …".
    Show how

    Start from this template and adapt it to your customers:

    We split first when:
- packets can contain many document types, or the types change often;
- different types need their own project, owner or release cycle;
- packets are long and we can skip pages we don't need, or they can exceed the model's page limit;
- the next system needs a page range per document (for example, to archive each one separately).
Otherwise we start with one project on the whole packet and check for mix-ups between groups.

    Back each point with what you measured in step 7 (scores, mix-ups, time, effort to add a type).

✅ What you should take away
  • Splitting first isn't always required. Decide based on how many types, how predictable the order is, how long the documents are, and how much review is needed.
  • IXP extracts; if you need splitting, it comes from a DU classifier in front of it.
  • Write down your decision rule and reuse it on every project.
