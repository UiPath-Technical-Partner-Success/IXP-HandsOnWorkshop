Lab 1 · Instructions & taxonomy design

⏱ ~35 min🔨 Hands-onSession 1
📖 Read first: Session 1 theory – Instructions & taxonomy design. It explains the instruction levels, the data types and how the scores are calculated, so each step below makes sense.
What you are doing and why

IXP (Intelligent Xtraction and Processing) uses an LLM (large language model) to read a document and fill in a structure you define, called the taxonomy. You steer the model with plain-language instructions, not with code and not by training it on examples.

In this lab you build a small taxonomy for bank statements, record a baseline score, then improve the weakest field by rewriting one instruction at the right level and measuring again.

At the end you have: an IXP project with a statement-header taxonomy, two reviewed statements, a baseline score, an improved score, and one written reason for the change you made.

In a real project this is the core build loop: agree which values the downstream process needs, extract, review the results against the true values, fix instructions one at a time, and show measured scores before go-live.

🎯 Objective

Learn what each instruction level does and where a fix belongs:

Level What it's for Seen by the model
Overall extraction instructions Rules that hold for every field in the project (document context, language, general conventions) On every extraction
Field group instructions What this group/section is and where it is in the document For all fields in the group
Field instructions What exactly this one field is, where it appears, an example value For that field
Field type instructions Rules shared by every field that uses this field type (e.g. "all amounts are in USD"). Only text that is true for all of those fields. For every field of that type

The model sees all levels together. A rule at one level that contradicts another level gives the model mixed signals. This lab uses the first three levels; the field type level is there so you know it exists.

Terms used in this lab

Already explained in Session 1 – Glossary, so not repeated here: project, taxonomy, field group, field, data type, prediction and annotation. Intelligent pre-processing is covered in Instructions & taxonomy design. New in this lab:

Precision / recall
Precision: the share of predicted values that are correct. Recall: the share of true values the model found.
F1 score
One number that combines precision and recall. It is high only when both are high.
Project score
The average F1 across all fields, shown on the Build tab.

New to UiPath? General terms such as DU (Document Understanding) and Automation Cloud are explained in Session 1 – Foundations.

✔️ Before you begin: prerequisites

  • Signed in to IXP (Intelligent Xtraction and Processing) in UiPath Automation Cloud
  • Sample files ready (listed below)

📎 Input files

bank_statement_B_3_accounts.pdf, bank_statement_C_2_accounts.pdf (or one of your own documents)

🔨 Steps

  1. 1
    Create a new IXP project for unstructured & complex documents. Name it Lab1_<your initials>. Upload both statements.
    Expected result: Project created, 2 documents uploaded.
    Why: a project holds your documents, taxonomy, instructions and scores in one place. "Unstructured and complex documents" is the IXP option for documents whose layout varies, such as bank statements from different banks.
  2. 2
    Create one field group Statement Header with fields: Bank Name (Exact Text), Account Holder (Exact Text), Statement Period (Inferred Text). Statement B prints only a month and C a free-text period, so a Date range would have nothing to match.
    Expected result: A taxonomy with one group and 3+ fields.
    Your first field group

    A field group collects values that belong together. Statement Header holds the values that appear once per statement; think of it as a one-row table with a column per field.

    Where: Build tab → Manage Taxonomy → Fields and field groups. Select Field group, enter a name and instructions, then under the group select Add → New field for each field. Fields can only be added inside an existing group. Select Save: all changes are applied at once.

  3. 3
    Check the field data types. Use the pre-configured field types wherever possible: Exact Text, Inferred Text, Number, Date, Monetary Quantity, Boolean. Create a custom Choice type only for a closed set of values.
    Expected result: Every field has a pre-configured type, unless you have a clear reason.
    Choosing a data type
    • Exact Text – the value appears word for word in the document (names, account numbers, IBANs, phone numbers). A phone number is Exact Text, not Number.
    • Inferred Text – the value can be derived from context, e.g. the language of the statement.
    • Number, Date, Monetary Quantity – the type normalises the value and fixes the output format.
    • Choice – the value is mapped to a fixed list. Each option has a display value and can have alternate values.

    Settle types now, before you review. A field type's data type cannot be changed once configured (you delete and recreate it), and switching a field to another field type later loses that field's existing annotations.

  4. 4
    Leave the instructions short on purpose (e.g. "Extract the bank name"). Run the extraction and look at the predictions on both documents.
    Expected result: A baseline. Some fields are likely wrong or empty.
    Why: you need a weak starting point to prove later that your rewrite helped. Where: Build tab → Validate predictions. If no predictions appear, select Predict extractions.
    📋 Ready-to-use instructions

    Weak on purpose: paste these to get your baseline. Leave the overall extraction instructions empty for now.

    Field group · Statement Header
    Statement header.
    Field · Bank Name (Exact Text)
    Extract the bank name.
    Field · Account Holder (Exact Text)
    Extract the account holder.
    Field · Statement Period (Inferred Text)
    Extract the statement period.
  5. 5
    Review the predictions field by field. Confirm only the values that are correct. Correct wrong values to the true value (mark a field as missing only if the value is not in the document), then submit each document.
    Expected result: Both documents fully reviewed: correct values confirmed, wrong values corrected.
    You are writing the reference answers

    Your confirmed and corrected values are the annotations. The scores compare the model's predictions against them. The model does not learn from them, so reviewing does not improve extraction; only instructions and model settings do.

    Two rules follow. Do not confirm a value without checking it: a wrong value you confirm counts as "correct" and inflates the score. Review every field and submit the document: unsubmitted changes stay as draft annotations, and partially annotated documents are left out of the scores.

    This review happens at design time on the Validate predictions page. Validation Station is the separate review screen people use in production; you meet it in Lab 4.

  6. 6
    Check the scores and write down the overall project score and each field's F1, precision and recall. The Build tab shows the project score; the Measure tab shows each field and field group.
    Expected result: Baseline scores recorded.
    Reading the scores
    • Low precision – the model returns values, but wrong ones. The instruction is too broad or ambiguous; tighten it with the label and location.
    • Low recall – the model misses values that are there. The instruction is too narrow or misses a format variant.
    • F1 combines both. Read it per field, not only the project score.

    With two documents each field has at most two values, so scores jump in big steps. That is fine for learning; for a real project the docs recommend at least 10 annotated examples per field. Scores appear once enough documents are validated; if the Measure tab is still empty, use the per-document error rate on the Build tab.

  7. 7
    Pick the worst field. Decide: is the problem specific to this field (→ field instruction), the whole section (→ group instruction), or the whole document (→ overall instruction)?
    Expected result: A written decision, with one sentence explaining why.
    Why: put each rule at the lowest level where it is always true. A field-level fix cannot break other fields; an overall rule reaches every field.
  8. 8
    Rewrite the instruction at the level you chose. Follow the pattern what + where + real example, e.g. "The customer the statement is addressed to, a company or a person. It is shown next to the label 'Customer' in the header block on page 1, directly above the address. Example: 'Beresheet Logistics Ltd.'"
    Expected result: Instruction updated.
    Where: Build → Manage Taxonomy (edit in the table, then Save), or on Validate predictions select the ellipsis (…) next to the field → Edit field. Describe the right value positively; leave date and amount formats to the data type.
    📋 Ready-to-use instructions

    Paste only the instruction for the level you chose in step 7, so you can see what that one change does. Add the others after step 9 if you want to see the full set working together.

    Overall extraction instructions
    These documents are bank statements from different banks. Each statement starts with the bank's name and a header block with the customer, address, statement period and statement number, followed by one section per account. Labels differ between banks (for example "Account number" or "Acct No."), so identify each value by its meaning, not by one specific label. Return text values as they are written in the document.
    Field group · Statement Header
    The statement header: the details printed once per statement at the top of page 1, between the bank's name and the first account section. It holds the customer, the address, the statement period and the statement number. Extract one occurrence per statement.
    Field · Bank Name (Exact Text)
    The name of the bank that issued the statement, printed as the large title at the top of page 1, above the bank's address line. Example: "Carmel Ridge Bank".
    Field · Account Holder (Exact Text)
    The customer the statement is addressed to, a company or a person. It is shown next to the label "Customer" in the header block on page 1, directly above the address. Return the name only. Example: "Beresheet Logistics Ltd.".
    Field · Statement Period (Inferred Text)
    The period the statement covers, shown next to the label "Statement period" in the header block on page 1. It can be a month, a date range or free text; return it as written. Examples: "September 2026", "Q3 2026 – September".
  9. 9
    Refresh the predictions and check the scores again. Compare with your baseline.
    Expected result: Score for that field improves; other fields stay about the same.
    How it works: open Validate predictions to see the new predictions (select Predict extractions if they do not refresh). Your annotations from step 5 stay in place, so the new predictions are scored against the same reference answers. LLM output varies slightly between runs, so do not read small changes as real. To compare with or restore an earlier instruction, select the ellipsis (…) → View change history.
  10. 10
    Experiment: put a rule in the overall instructions that is not true for every field (e.g. "All values are on page 1"). Evaluate again.
    Expected result: At least one field gets worse. That's why project-wide rules must hold for every field. Remove the rule.
    Why: the overall instructions are sent with every field, so one wrong project-wide rule misleads the model on all of them.
  11. 11
    Optional: open Build → Model configuration and try the other extraction model (GPT-4o or Gemini), or change intelligent pre-processing (None / Table model - mini / Table model). Evaluate.
    Expected result: You see how much model choice changes quality and speed for this document type.
    Model configuration

    Change one setting at a time and select Save. Switching the extraction model and saving creates a new project version and generates new predictions automatically, so you can compare against your previous scores.

    • Gemini is the recommended extraction model and handles up to 500 pages per call; GPT-4o is limited to 50 pages.
    • Table model - mini suits simple or several tables and is optimised for speed. Table model handles complex tables (nested tables, merged cells, tables across pages), adds latency and relies on Gemini models through the AI Trust Layer (UiPath's governance layer for calls to LLMs).
    • Instructions tuned for one model can score lower on another. Switch only if the other model fixes a real problem.
❓ Checkpoint questions
  1. Where would you put "The document is in French and English. Return values as written."? Why?
    Show answer
    In the overall extraction instructions. Language applies to the whole document and to every field, so the overall level is the lowest level where the rule is always true.
  2. A field returns the closing balance instead of the opening balance. Which level do you fix?
    Show answer
    The field instruction of that one field. Only one field is wrong, so a field-level fix can't break anything else. Describe the right value with what + where + example, e.g. "The balance at the start of the statement period, shown next to 'Opening balance' or 'Balance b/f' in the account section. Example: '62,480.00 ILS'." Then refresh the predictions and compare with your baseline.
  3. Why shouldn't you write "Format: DD/MM/YYYY" in a Date field instruction?
    Show answer
    The Date data type already normalizes the value and fixes the output format (YYYY-MM-DDT00:00:00Z). A format rule adds nothing and can conflict with the type. Use the instruction to say which date and where it is.
⚠️ Common mistakes
  • Writing format rules in instructions. The data type (Date, Monetary Quantity, Number) already sets the output format, and an instruction cannot change it. A format rule in the instruction conflicts with it. Inferred Text is the exception: there an instruction can normalise the output (e.g. a phone number as +1 (XXX) XXX-XXXX).
  • Very short instructions like "Extract the date". Say what the value means, where it is and give an example.
  • Saying what not to return ("Do NOT return the account number"). Describe the right value by label, role and location instead.
  • Creating custom types that copy a pre-configured one (e.g. a text-based Currency Amount type instead of Monetary Quantity). A text type does not normalise amounts the way Monetary Quantity does. Create a custom type only when no pre-configured type fits.
  • Changing several instructions at once. You can't tell which change helped.
  • Very long instructions. Each instruction has a character limit: up to 4,096 characters for every taxonomy element, raised from 2,048 in January 2026 (release notes; the design-time FAQ may still show the older figure). Shorter, focused instructions are easier to debug.
🚀 Stretch goals
  • Add an Inferred Text field such as Statement Language and see how it behaves compared with Exact Text.
    Show how

    Add a field Statement Language (Inferred Text) to the Statement Header group, with this instruction:

    The language the statement is written in, judged from the headings and labels of the whole document, not from one value. Return the language name in English. Example: "English".

    Expected result: "English" on both statements, because all samples are in English.

    What to compare: an Exact Text field copies a value that is printed word for word. The language is printed nowhere, so Exact Text has nothing to copy. Inferred Text derives the value from context, which is why its highlighted reference can be weak or missing. Judge the value, not the highlight.

  • Create a Choice data type for Account Type (e.g. Current, Savings, Deposit) and compare the results.
    Show how

    Account type is a closed set, so a custom Choice type fits. Create it with these options (display value, then alternate values):

    • Current: current account, business account
    • Savings
    • Deposit
    • Foreign Currency: foreign currency account

    Add a field Account Type with that type to the Statement Header group, with this instruction:

    The type of account the statement covers, taken from the statement title or the account heading, for example "Monthly Statement – Business Accounts" or "Foreign currency account (USD)". Pick the option that matches.

    Expected result: statement B → Current ("Business Accounts"), statement C → Foreign Currency.

    Why it's a good test: the samples never print "Savings" or "Deposit", and B never prints "Current". You see how a Choice maps the document's own wording to your list, and how alternate values help. A Choice type belongs to this project only, so you create it again in other projects.

✅ What you should take away
  • Field level is the default place to fix a field. Go to group or overall level only when the rule truly applies to the whole group or document.
  • Good instructions say what, where and an example, and leave formatting to the data type.
  • Your annotations are the reference answers: they produce the scores, they do not train the model.
  • Measure before and after every change.
