Theory · Instructions & taxonomy design

📅 Day 1📖 TheoryThen: Lab 1

✍️ Instructions & taxonomy design

⏱ Day 1 · 0:30–1:15 · Theory + Lab 1

Takeaway: design a small taxonomy around what the process needs, let data types do the formatting, put each instruction at the lowest level where it is always true, and change one thing at a time with a score before and after.

Taxonomy, field groups and data types

What it isThe taxonomy is the extraction schema. Field groups hold fields; each field has a data type. Each field group is a table and its fields are the columns. Hierarchy uses the > sign, for example Statement > Accounts.
What it doesIt defines the JSON shape the model fills. The data type normalises the value: Exact Text appears word for word (names, IDs, IBANs (International Bank Account Numbers), phone numbers); Inferred Text can be derived from context; Number, Date and Monetary Quantity have a fixed output format; Boolean is true/false; a custom Choice type maps values to a closed list.
When to useAlways, before you review a single document. One field group per logical section or entity; extract only what the downstream process uses. When not: there are no loose "generic" fields – put document-level values in a parent group for that document type.
How to use
  1. Build → Manage Taxonomy: create the field group, then add fields inside it.
  2. Use pre-configured types first; a phone number is Exact Text, not Number.
  3. Create a Choice type only for a closed set of values.
  4. Save: all inline edits land as one new project version.
Common mistakes
  • Splitting one entity across several groups (Customer Name, Customer Address as separate groups). Use one Customers group with three fields.
  • Copying a pre-configured type as a text type (a "Currency Amount" text type instead of Monetary Quantity) – you lose the built-in normalisation.
  • Changing types after review: a field type's data type cannot be changed once configured, and annotations cannot be remapped to a type with an incompatible data type.
  • Ignoring the documented limits: up to 32 fields per field group and 128 characters per field name.

The four instruction levels

What it isPlain-language instructions at four levels: overall extraction instructions (whole project), field group, field, and field type (shared by every field of that type). The model sees all of them together.
What it doesOverall: industry, document type, usual sections, and whether one file can contain several documents. Group: what this section or entity is, why it matters, where it sits, how to tell instances apart. Field: what the value means, where it appears, a real example. Field type: rules true for every field of that type (for example "all amounts are in USD").
When to useWrite a short overall instruction first, then group instructions, then tighten field instructions where scores show errors. Put each rule at the lowest level where it is always true. When not: do not use instructions to set formats for Date, Number or Monetary Quantity – the data type fixes those. (Inferred Text is the exception: an instruction can normalise it.)
How to use
  1. Field pattern: what + where + real example.
  2. Group pattern: section meaning + location ("header of page 1, under the title").
  3. Describe the right value positively; avoid "do not…".
  4. Edit in Manage Taxonomy or from the annotation pane (… → Edit field); use Change history to compare or restore.
Common mistakes
  • Contradictions between levels: the model gets mixed signals.
  • A project-wide rule that is not true for every field (Lab 1, step 10 shows the damage).
  • Vague one-liners ("capture the amount") give wrong values; over-narrow labels give missed values.
  • Expecting a parent group's instructions to reach its child group: they do not.
  • Very long instructions. The January 2026 release notes raised the per-instruction limit to 4,096 characters, while the design-time FAQ (frequently asked questions) page still shows 2,048 – check your tenant, and keep instructions short anyway.
Precision, recall and F1 in plain words

Precision: of the values the model returned, how many were right. Recall: of the values that are really in the documents, how many the model found. F1 combines both and is high only when both are high: F1 = 2 × P × R / (P + R). All three compare predictions with your annotations, so they are only as good as your review.

Measuring and iterating: annotations, scores and model settings

What it isThe build loop: review predictions, confirm or correct them (annotations), read the scores on the Build and Measure tabs, change one thing, refresh predictions, compare. Model configuration (Build → Model configuration) sets the extraction model and intelligent pre-processing.
What it doesAnnotations are the reference answers; the model does not learn from them. Improvement comes only from instructions and model configuration. Gemini is the recommended extraction model and the default for new projects; GPT-4o is the alternative. Pre-processing: None, Table model - mini (simple or several tables, faster) or Table model (complex tables, more latency, relies on Gemini). Switching model creates a new version and new predictions.
When to useAfter every meaningful change, on the same document set. The docs recommend reviewing 2–3 documents first, testing instructions on 20–30 representative documents, and at least 10 annotated examples per field for meaningful statistics. When not: do not change model and instructions in the same iteration.
How to use
  1. Read F1 per field, not only the project score.
  2. Low precision → tighten (label, location, disambiguator). Low recall → broaden (format variants, synonyms).
  3. Switch model only if it fixes a real problem; instructions tuned for one model can score lower on another.
  4. Record every score in a table.
Common mistakes
  • Blind-confirming: a wrong confirmed value counts as correct and inflates the score.
  • Leaving documents partially annotated: they are left out of the metrics.
  • Reading small score changes as real: LLM output varies slightly between runs.
  • Trying to fix OCR or layout problems with instructions; try pre-processing instead.
💬 "What does each prompt level do: overall, field group, field?"

Overall gives context for the whole project: the industry, the document type and its sections, and whether one file can hold several documents. Field group explains one section or entity: what it is, where it is, and how to recognise each instance. Field explains one value: what it means, where it is, and an example. A fourth level, field type, holds rules shared by all fields of one type. The model reads them all at once, so they must not contradict each other. Rule of thumb: one wrong field → fix the field; a whole section wrong → the group; wrong context or language → overall. Leave date and amount formats to the data type.

💡 Key takeaways
  • Field level is the default place for a fix; go higher only when the rule is true for everything below.
  • Good instructions say what, where and an example, and leave formatting to the data type.
  • Annotations are the reference answers: they produce the scores, they do not train the model.
  • One change, one measurement, one row in your score table.
