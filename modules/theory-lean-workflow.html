Theory · Lean workflow, confidence & validation

📅 Day 2📖 TheoryThen: Lab 4

⚙️ Lean workflow, confidence & validation

⏱ Day 2 · 0:50–1:45 · Theory + Lab 4

Takeaway: for one document type, a Studio workflow with Extract Document Data → your checks → validation only when a check fails → output is enough. Route on per-field confidence and business rules, and pick thresholds from runtime results on your own documents.

The lean IXP workflow vs. the DU Process template

What it isThe lean chain: get file → Extract Document Data (pointed at your IXP project and tag) → read values and confidence from Document Data → business rules + thresholds → Create Validation Task and Wait only if needed → write output. The Document Understanding Process template is the full Studio project template with logging, retries and exception handling.
What it doesExtract Document Data handles digitization and extraction in one activity and reads the field list straight from your IXP model, so you do not define a taxonomy in the workflow. The template adds production structure: one job per input file, with a dispatcher in front. It is Visual Basic only.
When to useLean: one document type per file, one model, a clear trigger upstream. Template: you need classification and splitting, several extractors or training loops, or you want its retries and logging as a starting point. When not: do not adopt the full template for a single-type IXP extraction just because "that is how DU is done".
How to use
  1. Install UiPath.DocumentUnderstanding.Activities in a version that supports IXP models (the IXP docs list the minimum).
  2. Extract Document Data: project, version (tag), document type, input file.
  3. Loop over field groups and fields; read value and Extraction Confidence Score.
  4. Set a needsReview flag from thresholds + rules; create a validation task only if it is true.
Common mistakes
  • Forgetting to publish and re-tag the improved model: the workflow keeps using the old version.
  • Mixing the Windows IntelligentOCR path (Data Extraction Scope + DU Project Extractor) with the cross-platform activities in one workflow.
  • Writing the original extraction to the output after a reviewer corrected it.
  • Removing parts of the template piecemeal and breaking its retry and exception paths.
Why confidence is runtime-only

IXP returns a confidence per field and per extraction when the model actually runs on a document. You see it in the extraction response and in Action Center, not on the IXP design-time screens, where you work with predictions and your annotations instead.

How confidence works: IXP vs. classic DU

What it isA 0–1 score per extracted value. IXP: returned per field at runtime in the model response and shown in Action Center, not in the IXP design-time UI. Classic DU ML extractors: come from a model trained on your labelled data; the DU docs describe them as a measure of the model's familiarity with the input, not true probabilities.
What it doesGives you one signal for deciding whether a person should look. The DU docs say confidence correlates only weakly with correctness and recommend business rules first; apply the same caution to IXP confidence. Different origin means different distributions: the DU docs note that thresholds differ per model, so a threshold that worked for a classic extractor or for OCR does not transfer to IXP.
When to usePer field, together with business rules, to route documents to review. When not: never as proof of correctness, and never with thresholds copied from another model or from OCR.
How to use
  1. Run a representative sample through the published model.
  2. Log value + Extraction Confidence Score per field (Lab 4 step 6).
  3. Compare confidence on correct vs wrong values; set each field's threshold where errors start.
  4. Re-check thresholds after any model, instruction or OCR change.
Common mistakes
  • Looking for confidence on the IXP screens: it is runtime only.
  • Reading 0 as "very uncertain": the docs note that when a model's token limit is exceeded, occurrence and extraction confidence come back as 0 and predictions may be incomplete.
  • Routing on confidence when it barely varies across fields on your sample – then rules carry the load.
  • Treating 1.00 as "certainly right": high-but-wrong values happen, which is why totals and ID checks matter.
Business rules

A business rule is a fixed check on the extracted data that does not depend on the model's confidence: a required field is present, net + tax = total, an IBAN has the right length, every account has a currency. Rules behave the same after a model or instruction change; confidence does not.

Thresholds, business rules and validation only when needed

What it isRouting logic you write in the workflow: a threshold per field (stricter for amounts and IDs, looser for descriptions) plus business rules. Any failure sets needsReview. Validation is not automatic: the IXP workflow docs describe human validation as triggered by decision logic in the workflow, using confidence thresholds and business rules.
What it doesSends only risky documents to a person. Create Validation Task and Wait (or Create Validation Task + Wait for Validation Task and Resume) creates an Action Center task; the robot pauses and continues with the validated Document Data. Validation Station colours confidence: below 50% red, 50–85% yellow, 86–99% light green, 100% green – display guidance, not recommended thresholds.
When to useAlways in production lean workflows; track the share of documents that go to a person as your key metric. When not: do not send every document "to be safe" – that removes most of the value of automation.
How to use
  1. List critical fields; start from a sample, not a global number.
  2. Add rules that do not depend on confidence.
  3. If needsReview: create the task with a clear Action Title and priority; Extracted fields validation confidence % filters which fields reviewers see.
  4. Export the validated Document Data (its results are also available as data tables); keep a confidence column for audit.
Common mistakes
  • One threshold for every field.
  • Trusting confidence alone, without rules.
  • Expecting reviewer corrections to improve the IXP model: there is no feedback loop from Action Center validation; improve instructions and publish a new version instead.
  • On the Windows path, forgetting that Export Extraction Results drops confidence unless IncludeConfidence is set (default False).
💬 "What's the best way to use IXP? Is there something lighter than the DU framework?"

Yes. For one document type, build a short Studio workflow: Extract Document Data pointed at your published IXP model, a few checks on per-field confidence and business rules, a validation task in Action Center only when a check fails, then write the output. Keep the full Document Understanding Process template for cases that need classification and splitting, several extractors or training loops, or its built-in retries, logging and exception handling.

💬 "How is confidence calculated in IXP, compared with classic DU?"

IXP returns confidence at runtime, per field and per extraction, and you see it in the model response and Action Center – not in the IXP design screens. Classic DU confidence comes from a model trained on your labelled documents and describes how familiar the input looks to that model. Same 0–1 scale, different origin, so never reuse a classic threshold for IXP. In both cases, build business rules first, use per-field confidence as a supplement, and re-tune after any model, OCR or instruction change.

💡 Key takeaways
  • Extract → rules → validate only when needed → output covers most single-type cases.
  • IXP confidence is runtime-only; pick thresholds from your own runtime sample.
  • Per-field thresholds plus business rules decide how much work goes to people.
  • Validation corrects the data, not the model.
