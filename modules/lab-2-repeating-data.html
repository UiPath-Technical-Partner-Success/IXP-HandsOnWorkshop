Lab 2 · Repeating data (several accounts in one document)

⏱ ~25 min🔨 Hands-onSession 1
📖 Read first: Session 1 theory – Repeating data. It explains why information that repeats belongs in one field group that returns one row per occurrence, and when to use parent and child groups.
What you are doing and why

Goal: teach IXP (Intelligent Xtraction and Processing) to read information that appears a different number of times in each document. A bank statement can list 2 accounts or 6; you want one design that handles any count without changes.

You build it two ways on purpose: first with numbered fields (Account 1, Account 2…), which is what most people try first, then with one field group that the model returns once per account. Comparing the two on the same three statements shows why the second design is the one to use.

At the end you have: an IXP project with an Account field group and a group instruction, reviewed predictions for 3 statements (4, 3 and 2 accounts), field group scores from the Measure tab, and a clean taxonomy with the flat experiment removed.

In a real project the same pattern covers most repeating data: statements with several accounts, invoices with line items, policies with several policy holders, portfolios with many holdings. Ask early "can this appear more than once?" for every value the business wants. Getting it wrong means rebuilding the taxonomy and re-reviewing documents later. Very long tables have a practical ceiling: the docs put reliable extraction at about 1,200 field values per document (Document processing limits).

🎯 Objective

In this lab you use IXP (Intelligent Xtraction and Processing), UiPath's tool for pulling data out of documents. You model the same information appearing several times in one document. Example: one bank statement with 4 accounts, one per currency. A field group is a set of related fields, for example everything that describes one account. The model predicts the group once per account, and each instance is called an extraction. You'll see why this is better than flat fields like Account 1 Balance, Account 2 Balance, and so on. The taxonomy is the list of fields and groups you ask the model to find. See Defining the taxonomy.

Terms used in this lab

Already explained earlier, so not repeated here: field group, data type, field group instructions, annotation and Validation Station in Session 1 – Glossary; repeatable field groups and key fields in Repeating data; precision and recall in Lab 1. New in this lab:

Instance / row / extraction
One occurrence of a field group in a document, for example one account. IXP calls each instance an extraction; in the table view it is one row.

New to UiPath? General terms such as DU (Document Understanding), Automation Cloud and taxonomy are explained in Session 1 – Foundations.

📋 Before you begin

✔️ Prerequisites

  • Lab 1 done (or a project with the 3 bank statements uploaded)

📎 Input files

bank_statement_A_4_accounts.pdf, bank_statement_B_3_accounts.pdf, bank_statement_C_2_accounts.pdf

🔨 Steps

  1. 1
    Create a project Lab2_<initials> and upload all 3 statements.
    Expected result: 3 documents (4, 3 and 2 accounts).
    Why: the three statements are your test set. They hold the same kind of data but a different number of accounts, so a good design must handle all three without changes. Where: create the project as in Lab 1 (Unstructured and complex documents).
  2. 2
    Approach A – flat fields (the wrong way, on purpose): in a group Accounts Flat, add Account 1 Number, Account 1 Currency, Account 1 Balance … up to Account 4. On the Validate predictions page, select Predict extractions to refresh the predictions.
    Expected result: Works for document A at best. On B and C the unused numbered fields stay empty and values can land in the wrong slot. A 5-account statement would need new fields.
    Creating a field group

    Where: Build tab → Manage Taxonomy → Fields and field groups. Select Field group, enter a name and instructions, then under the group select Add → New field for each field. Fields can only be added inside an existing group. Select Save: all changes are applied at once.

    Why build it the wrong way first: numbered fields are the design most people reach for. Seeing them fail on B and C, where some slots stay empty, makes the reason for approach B concrete.

  3. 3
    Approach B – one field group, many extractions: create a field group Account. You don't need a special setting: the fields in a field group can be predicted multiple times, once per account. Add fields: Account Number (Exact Text), Currency (Exact Text or a Choice), Opening Balance (Monetary Quantity), Closing Balance (Monetary Quantity). A field type tells the model what to expect: Exact Text copies the text as printed, a Choice picks from a fixed list you define, and Monetary Quantity reads an amount together with its currency.
    Expected result: One group definition, used for any number of accounts.
    How one group becomes many rows

    You describe one account. The fields defined under a field group can be predicted multiple times, as different instances of that group; each instance is one extraction, shown as one row. A 4-account statement returns 4 rows of the same 4 columns.

    Account Number is your key field: it is different for every account, so it keeps the rows apart even when two accounts share a currency. Create this group next to Accounts Flat, in the same way as in step 2.

    📋 Ready-to-use instructions

    Field instructions for the Account group (what + where + example). They work on all three statements because they name both label variants.

    Field · Account Number (Exact Text)
    The number of this account, shown next to "Account number" or "Acct No." at the top of the account's detail section, directly above the IBAN. This is the bank's account number, not the IBAN. Example: "400-552-918".
    Field · Currency (Exact Text)
    The currency of this account, shown next to "Currency" or "Ccy" in the account's detail section. The same currency also appears after each balance of that account. Example: "USD".
    Field · Opening Balance (Monetary Quantity)
    The balance of this account at the start of the statement period, shown next to "Opening balance" or "Balance b/f" (brought forward) in the account's detail section. Example: "62,480.00 ILS".
    Field · Closing Balance (Monetary Quantity)
    The balance of this account at the end of the statement period, shown next to "Closing balance" or "Balance c/f" (carried forward) in the account's detail section. Example: "61,737.40 ILS".
  4. 4
    Write the group instruction: "One occurrence per bank account listed on the statement. Each account has its own section with an account number, currency and balances. Extract every account, in the order they appear."
    Expected result: Group instruction saved.
    Why: the group instruction is where you say what counts as one instance and where in the document to find it. Without it, the model has to guess where one account ends and the next begins. Where: in Manage Taxonomy, select the group's instruction in the inline table, edit it and select Save. You can also do it from the Validate predictions page: field group ellipsis → Edit field group.
  5. 5
    Select Predict extractions again and open document A.
    Expected result: 4 extractions of Account, one per currency. If you get 8, or values mixed between sections, the page-1 summary table (it repeats every account) was read as extra accounts. Add to the group instruction: "One occurrence is one account detail section. The summary table on page 1 repeats these accounts and is not a separate account." Then select Predict extractions again.
    Why: predictions are not refreshed automatically after you change the taxonomy, so you select Predict extractions on the Validate predictions page to see the effect of the new group and its instruction.
    📋 Ready-to-use instructions

    If document A returns 8 extractions, replace the group instruction with this complete version. It includes the fix for the page-1 summary.

    Field group · Account (final version)
    One occurrence per bank account listed on the statement. Each account has its own detail section, which starts with a heading such as "ILS account 400-552-918" or "Account details – USD current account", followed by the account number, IBAN, currency and opening and closing balances, then a transaction table. Extract every account, in the order they appear. One occurrence is one account detail section. The summary table on page 1 repeats these accounts and is not a separate account.
  6. 6
    Check B and C.
    Expected result: 3 and 2 extractions, with no changes to the taxonomy.
    Why: this is the proof. The taxonomy did not change between documents; only the number of rows did.
  7. 7
    Review on the Validate predictions page: select the table icon to open the table view. Check each row against the document. Confirm correct rows. Confirm the entire field group in bulk only when every row is correct (Validating extraction predictions).
    Expected result: Correct rows confirmed. Wrong rows left unconfirmed.
    Reviewing repeating data

    Where: on the Validate predictions page, the table icon switches the field group from a list to a table: one row per extraction, one column per field. You can confirm from the side panel or from the table view.

    How to check: count the rows first. Fewer rows than account sections means a missed account; the same account number on two rows means one account was picked up twice. Then check the other values in each row against that account's section of the PDF (Portable Document Format) file.

    Your edits are stored as draft annotations, and the document shows as In progress, until you submit them. The Measure scores in step 8 ignore unannotated and partially annotated documents.

  8. 8
    Open the Measure tab (it shows how accurate the model is) and record the field group scores. Compare with approach A. With only 3 documents, treat the scores as indicative: the docs recommend at least 10 annotated examples per field for meaningful statistics (Gathering validation statistics).
    Expected result: Approach B handles every document without depending on the number of accounts.
    What the field group score means

    The Measure tab compares the model's predictions with your annotations. Select a field group to see its average F1, precision and recall, then select a field for its own scores. At group level, precision asks: of the extractions the model returned, how many were correct? Recall asks: of the true extractions, how many did the model find?

    These scores are not the model's confidence. IXP returns confidence scores in the model response and in Action Center at runtime, not in the design-time interface. A red dial on the Measure tab means there are not yet enough annotated examples, which is expected with 3 documents.

  9. 9
    Delete the Accounts Flat field group (Manage taxonomy › ellipsis › Delete). Its annotations (the values you confirmed) are lost, and you can only undo this by reverting to a previously published model version (Managing the taxonomy).
    Expected result: Clean taxonomy.
    Why: the taxonomy is the full list of what the model is asked to extract, so a leftover experiment keeps producing predictions on every document and clutters reviews and scores.
❓ Checkpoint questions
  1. A statement has 6 accounts. What do you change in approach B?
    Show answer
    Nothing. The Account group is extracted once per account, so a 6-account statement returns 6 rows. The document decides the count, not the taxonomy. Approach A would need new numbered fields for accounts 5 and 6.
  2. Two accounts share the same currency. How does the model keep them apart? Which field helps most?
    Show answer
    Each account is a separate extraction (one row) of the Account group, and the group instruction says that one occurrence is one account section. Account Number helps most: it is different for every account, so it keeps the rows apart even when the currency is the same.
  3. Where would you put "Ignore the summary table on page 1; extract each account from its own detail section"?
    Show answer
    In the field group instruction of Account. It defines what counts as one occurrence and where to find it. That is true for all fields of this group, but not for other groups, so the overall level would be too broad and a field level too narrow.
⚠️ Common mistakes
  • Numbered fields (Account 1…4) for data that repeats. They break as soon as the count changes.
  • Confirming a whole group when only some rows are correct. This confirms the wrong rows too. Confirm row by row in that case.
  • Picking up the same account twice (e.g. from the summary table and from the account section). Fix this in the group instruction by saying which part of the document to use.
  • Using Exact Text for amounts. Use Monetary Quantity so the amount and currency are handled together.
🚀 Stretch goals
  • Add a nested repeating structure: transactions per account (date, description, amount) as a child field group, Account > Transactions. Note that the parent group's instruction does not influence the child, so give the child its own instruction.
    Show how

    On the Account group, add a child field group Transactions. The parent's instruction does not reach the child, so the child instruction must stand on its own:

    One occurrence per transaction row in this account's transaction table. The columns are Date, Description, Debit, Credit and Balance (on some statements: Value date, Details, Paid out, Paid in and Running bal.). Each row between the opening balance row and the closing balance row is one transaction; the opening and closing balance rows are balances, not transactions. A table can continue onto the next page.

    Add these fields to Transactions. The table rows print no currency, so Number is simpler than Monetary Quantity here.

    Transaction Date (Date)

    The date of this transaction, in the first column of its row (labelled Date or Value date). Example: "01/09/2026".

    Description (Exact Text)

    The text that describes this transaction, in the Description or Details column of the same row. Example: "Transfer from savings".

    Debit (Number)

    The amount taken out of the account in this transaction, in the Debit or Paid out column of the same row. Rows that add money have no debit. Example: "41,230.60".

    Credit (Number)

    The amount paid into the account in this transaction, in the Credit or Paid in column of the same row. Rows that take money out have no credit. Example: "15,000.00".

    Expected result: statement B has 4 + 2 + 3 = 9 transactions, C has 3 + 2 = 5, and A has 14 across its 4 accounts. Remember that the parent is a gate: if an account is not found, its transactions are not returned either.

  • Add a business rule: Closing Balance = Opening Balance + sum of transactions. Implement it in your workflow after extraction, alongside confidence thresholds, and route failures to human validation (Consuming models via a workflow).
    Show how

    Once you have the Transactions group, the check is:

    expected = Opening Balance + sum(Credit) - sum(Debit)
if abs(expected - Closing Balance) > 0.01:
    mark the document as "needs review"

    Worked example (statement B, ILS account): 62,480.00 + (15,000.00 + 28,900.00) − (41,230.60 + 3,412.00) = 61,737.40, which matches the closing balance ✓.

    Where: add it next to the business rules in Lab 4, step 8, and run it per account. A failed rule sends the document to the validation task, like a low confidence score does. Use a small tolerance rather than exact equality, to allow for rounding.

✅ What you should take away
  • Repeating information = one field group, predicted once per item (one extraction per item).
  • Use table view in validation to review repeating data quickly.
