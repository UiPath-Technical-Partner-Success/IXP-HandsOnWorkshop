Theory · Multi-document files

📅 Day 2📖 TheoryThen: Lab 3

📚 Multi-document files (packets)

⏱ Day 2 · 0:05–0:45 · Theory + Lab 3

Takeaway: IXP extraction doesn't split a packet into documents: it returns your fields, not document boundaries. Either send the whole packet to one IXP project with a field group per document type (option B), or put a DU classifier in front that returns page ranges and send each range to its own project (option A). Choose by number of types, order, length and routing needs – and measure.

Packets, classification and splitting

A packet is one file with several documents inside, for example invoice + bank statement + payslip in one PDF. Classification decides which document type something is. Splitting finds where each document starts and ends and returns a page range per document ("pages 2–3: bank statement").

IXP is extraction only

What it isThe Unstructured and complex documents capability doesn't classify documents or find where one ends and the next begins. It extracts the fields you define from whatever file you send.
What it doesIt can read a stack of several document types in one file without splitting it first – the docs list this as a use case. But nothing in the output tells you where one document ends unless you ask for it in your taxonomy.
When to useKnow this before choosing A or B. When not: do not expect IXP to detect document boundaries or types for you, and do not send packets beyond your extraction model's page limit (per the model configuration page: GPT-4o up to 50 pages, Gemini 2.5 Flash up to 500 pages per call; pages beyond the limit are not processed). The Advanced extraction strategy (preview) reads a long or field-dense document in several passes, but it still returns one result, not a page range per document.
How to use
  1. Write down the document types a packet can contain and how they vary in order and length.
  2. Check packet length against the model's page limit.
  3. Decide A or B with the decision tree below.
Common mistakes
  • Believing "IXP will split my packet", including with the Advanced strategy.
  • Assuming one file equals one document.
  • Losing the page range, so a value cannot be traced back to its document.

Option B: one IXP project on the whole packet

What it isOne project whose taxonomy has one field group per document type (Invoice, Bank Account, Payslip). The whole file is sent as-is.
What it doesOne call, fewer moving parts. Each group instruction tells the model how to recognise its document ("Use only the document titled TAX INVOICE"), so fields are read from the right pages.
When to useFew, predictable document types, stable order, packets within the page limit, one downstream process. Fastest way to a proof of concept. When not: many types, variable order or count, long packets, or each type needs its own routing, reviewer or tuning.
How to use
  1. One field group per document type; a key field per group.
  2. Group instruction = visible clues (title, header text, typical labels) + what to ignore.
  3. Review every group for values taken from the wrong document.
  4. Re-evaluate all groups after any change.
Common mistakes
  • Weak group instructions: an account number from the payslip lands in Bank Account.
  • A taxonomy that grows with every new type: a change for one type can shift results for others.
  • Not checking packets in a different order (Lab 3, packet 2).

Option A: classify and split first, then IXP per type

What it isA DU classifier reads the packet and returns one entry per document: its type and page range. Your workflow sends each range to the IXP project for that type. In a Studio desktop (Windows) project this is typically a Classify Document Scope with the Intelligent Keyword Classifier, which is documented as able to split packages.
What it doesSeparates concerns: small, focused taxonomies per type, per-type scores, per-type routing and reuse in other processes. Consumption is metered per page, and a classifier in front of IXP is metered separately. When every page is extracted, A and B consume about the same; A saves only when it lets you skip pages you do not need. Check the licensing FAQ for your plan.
When to useMany types, variable order, long packets, per-type routing or review, or reuse of per-type projects. When not: small, predictable packets, where the extra step adds failure points without benefit. The DU trainable splitter is labelled Preview – do not base a production plan on it.
How to use
  1. Classify, then loop over the returned page ranges.
  2. Send each range to the matching IXP project; keep the page range with each result.
  3. Route unknown or low-confidence ranges to a person instead of guessing.
  4. Measure splitting accuracy separately from extraction accuracy.
Common mistakes
  • Not checking the split: a wrong boundary silently sends the wrong pages to the wrong project.
  • Over-splitting: a 2-page statement cut into two 1-page parts loses fields that span pages.
💬 "Several documents in one file: DU splitter then IXP, or a better way?"

It depends, and IXP extraction doesn't split packets for you. If your packets hold a few predictable document types and fit the page limit, start with one IXP project and one field group per type, with clear "how to recognise this document" instructions. If you have many types, a changing order, long packets, or each type needs its own routing or review, classify and split first with a DU classifier and send each page range to a dedicated IXP project. With a DU modern project classifier, the two consume about the same when every page is extracted; splitting saves only when you can skip irrelevant pages. Other classifiers are metered differently, so check the licensing pages. The real trade-off is complexity versus mix-ups, so pilot both on real packets and compare.

💡 Key takeaways
  • IXP extracts; splitting, if you need it, comes from a classifier in front of IXP.
  • Option B for few, predictable types; option A for many types, variable order, long packets or per-type routing.
  • Check the split before extraction and watch for over-splitting.
  • Write your rule down: "We split first when …".
