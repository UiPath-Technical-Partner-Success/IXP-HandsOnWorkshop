🧭 Using IXP well

⏱ Day 1 · 0:10–0:30 · Theory + discussion · Applied in Lab 1 (build) and Lab 4 (consume)

Takeaway: start new document projects in IXP, pick the capability by document type, and treat IXP as "measurable, governable extraction" – not as a smarter model. The value is everything around the LLM call.

IXP-first approach

What it isA design stance: for a new document project, start by choosing the IXP capability that matches the documents, instead of writing your own LLM prompt or building a custom model.
What it doesIt solves the problems teams hit when they build LLM extraction by hand: testing several models, slow prompt iteration, no ground truth, no metrics, no way to compare a change, schemas that are hard to maintain, and no version control over what runs in production.
When to useLayouts vary, values must be inferred, tables are complex, several document types sit in one file, or you need measurement and governance from day one. When not: fixed-layout, high-volume documents with a strong DU out-of-the-box model (for example invoices) may fit DU Modern better. Check the page limit of your extraction model for very long documents.
How to use
  1. Run the docs' capability decision guide for the use case.
  2. Prototype on a representative sample: review 2–3 documents first, then grow to the 20–30 the docs recommend.
  3. Iterate instructions, measure, publish and tag a version.
  4. Consume from a workflow and validate only exceptions.
Common mistakes
  • Starting from the tool ("we have IXP, let's use it") instead of from the data and the decision it feeds.
  • Prototyping on one "nice" document and discovering layout variation in production.
  • Promising speed or accuracy before measuring on the customer's own documents.

IXP vs. sending a PDF straight to an LLM

What it isA comparison between a governed extraction capability and a raw completion call (file + prompt → LLM → JSON, a plain-text data format). Both use an LLM underneath.
What it doesIXP adds: digitization (OCR), a typed schema (the taxonomy), a Measure page with precision, recall and F1 per field, a confidence per value at runtime, Validation Station and Action Center for review, published versions with Staging and Production tags, change history per field, and governance through the AI Trust Layer (UiPath's control layer for LLM calls).
When to useIXP whenever the result feeds a business process, needs an audit trail, or must be measured before go-live. When a plain LLM call is fine: one-off, low-risk, low-volume tasks with no audit or review need.
How to use
  1. Frame it as "the same kind of model, plus what production needs".
  2. Run both on the same 20–30 documents if a customer asks, and compare accuracy, time and review effort.
  3. Check metering on the licensing pages; IXP is charged per page per operation.
Common mistakes
  • Claiming IXP is always more accurate or always cheaper. Measure on your own documents; a bare LLM call can be faster.
  • Forgetting the hidden work of the raw approach: schema validation, a review UI, metrics and version control all have to be built and maintained.
  • Quoting prices from memory instead of the customer's licensing plan.

The GA ways to consume an IXP model

What it isA published, tagged IXP model can be called from several places. GA (generally available, meaning supported for production) and documented: the Extract Document Data activity in Studio and Studio Web (UiPath.DocumentUnderstanding.Activities), the Document Understanding Project Extractor in the Windows IntelligentOCR package, and the Document Understanding Cloud API (API: application programming interface, a way for one program to call another). The IXP tool in Agents is announced in the Agents release notes as Preview.
What it doesEach caller picks the project and a tag (Staging or Production) and gets back the structured result with confidence. Publishing freezes a snapshot of your instructions; the tag tells callers which snapshot to use, so later edits in IXP do not change production until you publish and re-tag.
When to useActivities: the default for RPA (robotic process automation) developers. DU Cloud API: callers outside UiPath; synchronous calls handle up to 5 pages, use asynchronous calls (start + poll) for longer documents and volume. Agents IXP tool (Preview): an agent needs structured data from a document; access also depends on your cloud platform, so do not base a production plan on it.
How to use
  1. In IXP, publish a version and mark it as Staging or Production.
  2. In the caller, select the project and the tag.
  3. Read values and confidence from the result.
  4. Add validation only where your rules require it.
Common mistakes
  • Forgetting to publish and re-tag after improving instructions: the robot keeps running the old version.
  • Pinning a package version from a blog post. The IXP docs list the minimum package versions; check them in Manage Packages.
  • Using the synchronous API for long documents.
  • Building on Preview paths for production plans. The docs label the Agents IXP tool, coded workflows (DU coded automation APIs) and IXP in Maestro Flow as Preview.
Publish, tag, consume

A published version is a frozen copy of your project's configuration. A tag (Staging or Production) is a label on one version. Callers ask for "the Production version of project X", so you can keep editing in IXP without affecting the robot, then move the tag when the new version scores better.

💬 "Why IXP, and not just send the PDF straight to an LLM?"

Both use the same kind of model. The difference is what surrounds it. With IXP you get a schema the model must fill, OCR for scanned pages, scores per field so you can prove quality before go-live, a confidence per value so you can send only doubtful documents to a person, a ready-made review screen, and versions you can roll back. With a raw LLM call you build all of that yourself. Be honest about the trade-offs: IXP extraction doesn't classify or split packets, does not learn from corrections, and can be slower than a bare call. Measure both on your own documents.

💡 Key takeaways
  • Pick the IXP capability by document type; Unstructured and complex documents is for variable, complex or stacked documents.
  • IXP's value over a raw LLM is measurement, validation and governance, not a "better model".
  • GA consumption: Extract Document Data, DU Project Extractor, DU Cloud API. The Agents IXP tool, coded workflows and IXP in Flow are Preview.
  • Production runs the tagged version: publish and re-tag after every improvement.
