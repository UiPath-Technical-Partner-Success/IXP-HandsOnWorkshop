Lab 4 · Lean workflow, confidence & validation

⏱ ~40 min🔨 Hands-onSession 1
📖 Read first: Session 1 theory – Lean workflow, confidence & validation. It explains when a single Extract Document Data activity is enough instead of the full DU (Document Understanding) framework, where IXP (Intelligent Xtraction and Processing) confidence scores come from, and how to decide which documents a person must check.
What you are doing and why

Goal: in Lab 2 you taught an IXP model to read bank statements. A model does nothing on its own until an automation calls it. Here you build the smallest useful automation: a Studio workflow that sends a PDF to the model, checks the answers, asks a person to look only when something seems off, and saves the result.

What you will have at the end: a Studio process Lab4_LeanIXP that extracts the bank-statement fields, flags risky documents using confidence plus business rules, opens a validation task only for flagged documents, writes an output file and logs how long each step took.

How it maps to a real project: this is the core of most production automations for one document type. In a customer project you add a trigger in front (mailbox, shared folder, queue), send the output to the downstream system instead of a file, and add error handling. The thresholds and rules you write here decide how much work still lands on people, so they are the part the business will ask about.

🎯 Objective

Build a light Studio workflow that uses an IXP model without the full DU framework:

Get file → Extract (IXP model) → Check confidence + business rules
        → valid?  yes → output
                  no  → validation task (Validation Station) → output

You'll also measure how long each step takes.

📋 Before you begin

✔️ Prerequisites

  • Studio Web open on the workshop tenant (Setup & access, steps 3–5)
  • The UiPath.DocumentUnderstanding.Activities package added to your Studio Web project, in a version that supports IXP models. The IXP docs list the minimum version; check it in the project's package manager (the IXP model option may not appear in older versions).
  • An Orchestrator folder you can use, with a storage bucket for the validation task (prepared on the lab tenant)
  • Your Lab 2 project (bank statements)

📎 Input files

bank_statement_A_4_accounts.pdf, bank_statement_B_3_accounts.pdf

Terms used in this lab

This lab adds no new terms. Everything it uses is explained earlier: Studio, robot, Orchestrator, Action Center, DU and IXP in Session 1 – Foundations; Document Data, confidence, Validation Station and HITL (human in the loop) in Session 1 – Glossary; Extract Document Data in Using IXP well; the DU framework, thresholds and business rules in Lean workflow, confidence & validation; the Account field group in Lab 2.

🔨 Part 1 – Make the model available at runtime

  1. 1
    In your Lab 2 project, publish the latest model version, then in the Publish tab use the ellipsis next to it and select Mark as production.
    Why
    Studio can only call a published model version. Publishing freezes a snapshot of your instructions; the tag (Staging or Production in the IXP UI) tells consumers which snapshot to use, so later edits in IXP do not change what the robot runs until you publish a new version and mark it as production.
    Expected result: A published version marked as Production.
  2. 2
    Note the IXP project name and check which version carries the Production tag. You select both in Studio in step 4.
    Orchestrator folder
    A folder in Orchestrator groups robots, processes and resources and controls who can use them. In this lab the validation task (step 9) is created in your Orchestrator folder, and the documents and data it needs are stored in an Orchestrator storage bucket.
    Expected result: You know the project name and tag to select in Studio.

🔨 Part 2 – Build the workflow

  1. 3
    Create a new process Lab4_LeanIXP in Studio Web. Add a variable for the input file path and a log message with a timestamp at the start.
    How and why
    In Studio, a process is a project a robot runs from start to end. In Studio Web the process runs on a cloud robot, which can't read files on your computer. Make the sample PDF available to the robot first, for example by adding it to the project files or reading it from the workshop storage bucket, and point the file path variable at it. The trainer shows the way that works on the workshop tenant. Add a Log Message activity with a message such as "Start " + Now.ToString("HH:mm:ss.fff") (VB) or "Start " + DateTime.Now.ToString("HH:mm:ss.fff") (C#). These timestamps feed the timing table in Part 4.
    Expected result: Empty process with a start time log.
  2. 4
    Add Extract Document Data (Document Understanding activities). Select your IXP project, its Production tag and the input file. Save the output to a variable. (Property names may differ slightly by version.)
    What this activity does and what to expect
    This single activity replaces the separate digitize and extract steps of the DU framework. IXP only extracts (it does not classify), and the activity reads the field list straight from your IXP model, so you do not define a taxonomy in the workflow. In its properties you pick the Project, the Version (tag) and the Document Type. The input is a file, the output is a Document Data variable.
    Expected result: The activity returns extraction results.
  3. 5
    Log a timestamp after extraction.
    Expected result: You can see the extraction time in the logs.
  4. 6
    Loop through the extracted fields (including every occurrence of the Account group). For each field, read its value and confidence.
    Field groups and confidence
    The Account field group repeats once per account on the statement, so you need two loops: one over the group occurrences (one per account) and one over the fields inside each occurrence. For each field read the value and the Extraction Confidence Score. The IXP design screens do not show confidence; this log is the first place you see it, which is why later thresholds must come from runtime output like this.
    Expected result: Values and confidences printed to the log.
  5. 7
    Add the confidence rule: if any key field (e.g. Account Number, Closing Balance) is below your threshold (start with 0.8), mark the document as "needs review".
    What the score means
    The score (0 to 1) is how sure the model was about that value. It is not a calibrated probability: high-but-wrong and low-but-right both happen, so 0.8 is only a starting point. Use a separate threshold per field – stricter for amounts and IDs, looser for descriptive text. One documented case to recognise: a value of 0 can also mean the model's token limit was exceeded (the response then returns occurrence and extraction confidence values of 0), not just "very uncertain".
    Expected result: Flag set correctly.
  6. 8
    Add at least one business rule that doesn't rely on confidence, e.g.: the number of accounts > 0; every account has a currency; Closing Balance is not empty. If a rule fails, mark "needs review".
    Why
    Rules catch errors that confidence misses: a value the model was confident about but that is wrong, or a field it skipped entirely. Rules are deterministic, so they behave the same after a model or instruction change; confidence does not.
    Expected result: Flag also set by business rules.
  7. 9
    If "needs review": create a validation task (Action Center / Validation Station) and wait for it to complete – use Create Validation Task and Wait, or Create Validation Task followed by Wait for Validation Task and Resume. If not: skip validation. (Activity names may differ slightly by version.)
    Validation task: settings and what to expect
    Pass the Document Data from step 4 as the extracted data and give the task a clear Action Title (e.g. the file name) and a priority (Low, Medium, High, Critical; default Medium). Set Display Mode to Compact: field groups and the field filters used in Part 3 are supported in the compact view only. The Extracted fields validation confidence % property sets the upper limit confidence score used for filtering extracted fields, so reviewers can focus on fields below your bar. The task appears in Action Center; the robot pauses until a person completes it, then continues with the validated Document Data. Create Validation Task and Wait is documented for Studio from Automation Cloud and works only together with Extract Document Data. (Present Validation Station, for attended review on the robot's machine, belongs to the IntelligentOCR package for Windows projects and does not take Document Data, so it does not fit this workflow.)
    Expected result: Validation only happens when needed.
  8. 10
    Write the final values to an output (e.g. a DataTable, an Excel file or a JSON (JavaScript Object Notation) file). Log the end timestamp.
    Watch out
    If a validation task ran, write the validated Document Data, not the original extraction – otherwise the reviewer's corrections are lost. Document Data can also expose its results as data tables that you write with Excel or CSV activities. Keeping a confidence column in the output makes it easy to audit later why a document was or was not reviewed.
    Expected result: Output file and total runtime in the log.
  9. 11
    Run with bank_statement_A_4_accounts.pdf. Then lower the threshold to 0.5 and raise it to 0.95, and run again each time.
    How to read the result
    With one document you are watching whether this document flips into review, and which field caused it – log the field name that triggered the flag. In production the same experiment over a representative sample gives you the validation rate per threshold. If the confidence values barely vary between fields, changing the threshold changes little, so lean on business rules.
    Expected result: You see how the threshold changes how many documents go to people.

🔨 Part 3 – Validation Station

  1. 12
    Open a validation task. Review the Account group as a table (for IXP Unstructured and complex documents, all extractions are validated as tables), use Confirm all cells to confirm a whole table, and use field filters (e.g. the Hide fields menu with Confirmed ticked, to see only what is left to check; compact view only).
    Validation Station
    Open the task from Action Center. The document is on one side and the extracted values on the other; click a value to see where it came from on the page, correct it if needed, then confirm. Confidence is colour-coded: below 50% red, 50–85% yellow, 86–99% light green, 100% green. These bands are display guidance, not recommended thresholds. Completing the task sends the validated data back to the waiting robot. Corrections here do not retrain the IXP model; to improve it, refine the instructions in IXP and publish a new version.
    Expected result: You know the review features that save time on repeating data.

❓ Checkpoint questions
  1. Why use business rules as well as confidence?
    Show answer
    Confidence is not a calibrated probability: high-but-wrong and low-but-right values both happen, and 0 can also mean the token limit was exceeded. Business rules (required fields present, at least one account, a currency on every account) are deterministic. They catch errors that confidence misses, and they behave the same after a model or instruction change.
  2. What threshold would you start with in production, and how would you adjust it over time?
    Show answer
    Start around 0.8 for key fields, stricter for amounts and IDs and looser for descriptive text. Run a representative sample and track two numbers: the validation rate (share sent to people) and the errors that get through without review. Raise a field's threshold if wrong values slip through; lower it if people mostly confirm correct values. Re-check after every model or instruction change.
  3. Which parts of the full DU framework does your customer actually need (retries, exception handling, logging – and queue-based dispatching, which is the dispatcher's job, not the template's)? Which can you leave out?
    Show answer
    There is no single right answer; it depends on the customer. Usually you keep retries for transient errors, exception handling and logging (including timings). Queue-based dispatching belongs to the dispatcher. For one document type with Extract Document Data you can usually leave out the separate digitize and classify steps and the taxonomy in the workflow.
⚠️ Common mistakes
  • One threshold for every field. Critical fields (amounts, IDs) usually need a stricter threshold than descriptive ones.
  • Trusting confidence alone. Always add simple business rules (required fields, totals adding up, valid currencies).
  • Treating confidence as a probability that's calibrated for your documents. Check how confidence behaves on your documents before you pick thresholds. If you route on OCR (optical character recognition) confidence, recheck those thresholds when the OCR engine is updated.
  • Not checking how the chosen model reports confidence. Exceeding the token limit returns a confidence of 0, which is not the same as "very uncertain". Run a sample first; if confidence barely varies, routing on it adds little.
  • Looking for confidence in the IXP screens. It is only returned at runtime (in the model response and in Action Center). Pick thresholds from a sample run through the published model, and recheck them after model, instruction or OCR changes.
  • Sending every document to validation "to be safe". That loses most of the value of automation.
  • Forgetting to publish the new model version and mark it as production after improving instructions. The workflow keeps using the old one.
🚀 Stretch goals
  • Add a retry and an error branch (file can't be read, extraction fails).
    Show how

    Activity names may differ slightly by version.

    1. Put a Retry Scope around Extract Document Data (for example 3 retries, a few seconds apart). This covers temporary errors such as a timeout or a busy service.
    2. Put a Try Catch around the processing of each document. In the catch: log the error with the file name, mark or move the file as failed, and continue with the next file.
    3. Don't retry errors that won't go away by themselves: a missing, locked, corrupt or password-protected file, or a failed business rule. Send these straight to the error branch or to validation.

    Test it: rename one input file so it can't be found, and check that the workflow logs it and continues.

  • Run 10 documents in parallel and compare the total time with running them one after another.
    Show how
    1. Make 10 copies of the bank statements (for example 5 of A and 5 of B) in one folder.
    2. Run them once with For Each (one after another) and once with Parallel For Each. Log the start and end time per document and in total.
    3. Skip the validation branch for this run, or use Create Validation Task without waiting, so open tasks don't hold up the run.

    What to expect: the parallel run finishes sooner, but not 10 times sooner. Service limits and the slowest document set the pace. In production, the usual way to scale is a queue that several robots work through.

✅ What you should take away
  • You don't always need the full DU framework: extract → rules → validate only when needed → output covers many cases.
  • Confidence thresholds plus business rules decide how much work goes to people. Tune them with real data.
  • Measure time per step before you try to optimize.
